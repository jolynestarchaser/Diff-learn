# Explicit local hunk review

`dr review mark`, `list`, and `reset` manage acknowledgments in `<root>/.difflearn/review-state.json`. This is local user state, separate from Git/file/hunk evidence, syntax/candidate facts, and their schemas. No collection or context command reads or writes acknowledgments. **Reviewed means a user explicitly acknowledged the cited hunk; it does not mean correct, safe, understood, tested, or approved for release.**

Evidence loading accepts versioned 1.0.0/1.1.0/1.2.0 and Java 1.3.0 exports without loading native parsers. `dr ui --evidence` shares that validation but remains a read-only captured-export viewer: copy handoff does not acknowledge or update review state. Review writes and live refresh in the UI are follow-up work; use the explicit terminal commands below for acknowledgments.

## Commands and snapshots

```sh
dr review list --root . --evidence .difflearn/evidence.json
dr review list --root . --evidence .difflearn/evidence.json --json
dr review mark --root . --evidence .difflearn/evidence.json --snapshot <snapshot-id> --hunk <hunk-evidence-id>
dr review reset --root . --json
```

Mark requires explicit hunk IDs (repeat `--hunk`) and exactly one repository snapshot ID. All targets must be collected hunks in that snapshot; a comparison, file, symbol, unknown ID, duplicate ID or mismatched snapshot fails before any acknowledgment is written. All requested marks succeed together or none does. There is no mark-all or automatic mark-on-context operation. Listing includes concrete snapshot/comparison/hunk/file IDs, scope, byte path, normalized fingerprint, status/reason, and the original acknowledgment citation where matched.

Input is an explicitly saved, runtime-validated evidence bundle, version 1.0.0, 1.1.0 or 1.2.0. IDs and parent/range invariants are checked. `--root` defaults to invocation cwd and must match the export's canonical workspace. An exported snapshot can be historical: marking it acknowledges that recorded snapshot, not an unseen current working tree. Recollect and export evidence to list a later snapshot. After relocating a workspace, recollect before using its old local state. Stable repository keys may survive relocation; absolute paths are locators, not matching identity. Changing a workspace's repository keys deliberately invalidates continuity. Keep local state local to its workspace; it is not a signed or authenticated audit trail.

No Git collection, network requests, source rereads, scripts or tests are invoked by these commands. `list` is read-only, including when state is absent. Only `mark` and `reset` create/write state. Explicit reset discards **all** acknowledgments, including corrupt/version-incompatible data, and writes a validated empty state. It does not delete exports. To retain invalid data for inspection, copy the state file before resetting. The discarded acknowledgment count is `null` when unknown.

`--json` emits one English-keyed report (`reportKind: review`, schema 1.0.0); fatal failures use the existing JSON error envelope. Warnings/errors go to stderr. Human output supports `--lang en|th`, retaining paths, IDs, scopes and reason codes. Review locale defaults to English and does not load `.difflearn.json`. Exits: 0 successful operation/complete input; 1 incomplete input, a pending writer lock, JSON read/parse failure or operational/state failure; 2 invalid flags, evidence schema/citations or targets; 130 SIGINT. A partial-input mark may write acknowledgments for complete, unambiguous file patches and still exit 1. Input coverage is always disclosed; missing hunks are never interpreted as reviewed.

## Conservative continuity

Matching uses stable repository ID plus a versioned comparison context: scope, attached/unborn branch (or detached HEAD commit), base input and resolved commit, typed before endpoint (including its immutable commit when present), captured configuration/attribute hashes, and comparison policy. Worktrees, branches, base names/commits and scopes remain isolated. Advancing the staged before-HEAD commit or changing an unstaged before-index blob invalidates matching. Line numbers alone never establish identity; ordinals, headings, locale, absolute root paths and timestamps do not establish it either. For existing files, continuity additionally requires the same recorded old-side range **within the same immutable old blob**, together with the content/context checks. Thus an identical single edit moving between repeated regions of that blob becomes unseen. New-side range shifts can retain status; shifts in a changed before-blob conservatively invalidate it.

The normalized content fingerprint is SHA-256 over canonical, ordered line operations, exact base64 bytes and both sides' no-final-newline facts. It removes patch presentation locations/headings, **not** whitespace, Unicode distinctions or CRLF bytes. Before-region fingerprints use ordered old-side content bytes and newline flags, excluding added lines. State stores fingerprints and citations, not source text. Its acknowledgment ID is deterministic over the full typed acknowledgment, with a separate hash for comparison context.

- **Unseen:** no uniquely justified acknowledgment, changed context/before blob, incomplete/unsupported file patch, or ambiguous matching. Identical full-content hunks within the same file/comparison are always unseen and cannot be marked, even in the original snapshot. Complete inventories are required to rule out hidden duplicates.
- **Reviewed:** one acknowledgment matches exactly, or a unique content fingerprint and unique before region agree within the same file lineage/context and old blob. Range shifts alone can retain status. A newly added file with no before region may retain only a unique, identical full fingerprint; an edit to it becomes unseen.
- **Changed-since-reviewed:** one-to-one matching establishes the same unique old-side region in the same immutable before blob and file/context, but full content differs. This is content continuity, not semantic identity. Changed context lines, hunk splitting/merging, repeated before regions or multiple competing acknowledgments conservatively lose continuity. No fuzzy similarity, nearest-line choice or textual symbol identity is used.

Paths normally match exactly by raw bytes. Only Git's authoritative `R` metadata can move a previous path acknowledgment: original paths and immutable old blob/mode must agree, and the hunk match must remain unique. Delete/add pairs never imply a rename. Pure renames have no hunks to acknowledge. Collisions or a single acknowledgment competing for multiple current hunks remain unseen. Marking a uniquely matched changed hunk replaces its previous acknowledgment with the supplied snapshot citation; unrelated contexts remain untouched until reset. Old absent hunks remain in state without being assigned to new observations.

## Storage, failures and limits

The [state schema](review-state.schema.json) and [output/error schema](review-output.schema.json) are generated from strict runtime schemas. State version/policy mismatches, malformed UTF-8/JSON, unknown fields, duplicate IDs, tampered fingerprint identities, oversized files and concurrent read mutations fail visibly. Unsupported versions are not migrated or silently replaced. The fixed `.difflearn` directory cannot be a symlink/junction, and state/evidence JSON must be regular files. `.difflearn/` is already ignored by this package and excluded by discovery/corpus defaults; consuming repositories should also ignore it to avoid tracking local state/exports.

Writers acquire an exclusive `review-state.lock`, validate/read the last committed state while holding it, write a uniquely named temporary file in the same directory, flush and close it, then replace state with one rename. They never delete the previous state to force replacement. Abort/failure before replacement preserves the previous state and cleans up that writer's files; a killed process can leave its lock/temp file. Readers only read `review-state.json`; they never recover/promote temporary content. An observed lock yields a warning and partial listing, and blocks writes, including reset. After confirming its writer has stopped, an operator may manually remove that lock and orphan temp files. There is no age/timestamp-based lock stealing. Concurrent marks cannot silently overwrite each other's reads.

This uses [Node 24 file handles/flush](https://nodejs.org/download/release/v24.20.0/docs/api/fs.html#filehandlesync), [exclusive open](https://nodejs.org/download/release/v24.20.0/docs/api/fs.html#file-system-flags), and [rename](https://nodejs.org/download/release/v24.20.0/docs/api/fs.html#fspromisesrenameoldpath-newpath). Parent-directory fsync follows replacement on non-Windows systems; Windows has no portable directory flush through this API. Atomic visibility on a local filesystem is the intended guarantee, not durability across power loss, arbitrary network filesystems, malicious concurrent directory replacement, or a hardware failure. An error after replacement may leave the new committed state: list it before retrying.

Explicit bounds: input evidence 64 MiB, state 16 MiB, 20,000 stored acknowledgments and 20,000 listed hunks. Exceeding a bound fails visibly without silently dropping records. Partial/truncated evidence cannot acknowledge incomplete file patches; binary/conflict/metadata-only representations have no acknowledgeable text hunks. State contains no review timestamps; physical filesystem metadata is used only for read consistency, never review matching.

Synthetic fixtures cover unchanged snapshots, shifted ranges, edited content, identical/repeated before regions, competing acknowledgments, authoritative renames versus delete/add, changed before blobs, separate bases/branches/scopes/detached commits/worktrees, partial/unavailable snapshots, schema corruption, read-only context, stdout parsing, concurrent writers, pre-rename abort/failure, a killed writer, and symlink/junction bounds. These checks establish the implemented matching policy, not correctness of the reviewed source.
